Balcony Station Receiver — Build Spec

For: Claude Code, developing on Carlos's Windows laptop and deploying to his Contabo VPS. Goal: Run a small always-on receiver on the VPS that stores readings sent over HTTPS by an ESP32 sensor node on the balcony, with a private dashboard to view them.

1. Context

[ESP32-C6 node on balcony, AA batteries]
   wakes every ~10 min → reads sensors → saves reading in its flash memory
   → uploads about hourly by HTTPS POST → on success, deletes the readings the VPS acknowledged
                │  (home WiFi, then the internet, encrypted)
                ▼
[nginx on the VPS: station.carlosgorrichoai.one]
   TLS, rate limiting, public paths only
                │
                ▼
[This receiver in a Docker container, bound to 127.0.0.1]
   validates → stores in SQLite (no duplicates) → acks highest seq stored with no gaps

[Carlos's browser] → HTTPS → nginx login → /dashboard
  • Home internet can drop, and hourly uploads save battery compared with uploading every reading. The node buffers readings and resends them in batches. The receiver must accept batches, tolerate resends and out-of-order data, and never store duplicates.
  • Frost/heat alerts are not this receiver's job. The node pushes them directly to Carlos's phone.
  • Readings leave the home network, encrypted, and are stored only on Carlos's VPS. No third-party cloud service.

5. API contract (the ESP32 firmware will be written to match this exactly)

The node connects to https://station.carlosgorrichoai.one. HTTPS is required, and the node must verify the server certificate. Plain HTTP would expose the API key.

All requests from the node carry the header X-Station-Key: <STATION_API_KEY>. A missing or wrong key returns 401.

PathReachable from
POST /api/v1/readings, GET /api/v1/timeThe internet, rate limited
/dashboardThe internet, behind the nginx login
/api/v1/health, /api/v1/latestThe VPS only. nginx returns 404
Everything else, including /docsNowhere. Turned off in the app, and nginx returns 404

5.1 POST /api/v1/readings

Request body:

{
  "node_id": "balcony-01",
  "fw_version": "0.1.0",
  "oldest_buffered_seq": 1003,
  "readings": [
    {
      "seq": 1042,
      "ts": 1762538400,
      "ts_synced": true,
      "metrics": {
        "air_temp_c": 18.4,
        "air_rh_pct": 52.1,
        "lux": 61234.0,
        "tray_temp_c": 21.7,
        "pellet_moisture_raw": 1830,
        "battery_v": 4.71,
        "power_source": "battery",
        "rssi_dbm": -61
      }
    }
  ]
}

Rules: - seq: a monotonically increasing integer per node, kept across deep sleep. (node_id, seq) is the unique key. Duplicates are silently ignored, not errors. - oldest_buffered_seq: required. The lowest seq still in the node's buffer. It must not be higher than the lowest seq in the batch; otherwise return 422. Anything below it can never be resent, so the receiver does not wait for it. - ts: Unix epoch seconds, UTC, from the node's clock. ts_synced is false if the node hasn't synced its clock recently. Store it anyway. - metrics: an open dictionary. Unknown metric names must be accepted and stored, so new sensors can be added later without changing the receiver. Values are numbers, or short strings (e.g. power_source). - Batches hold 1 to 500 readings. Readings may arrive out of order. - seq and ts are non-negative JSON integers. node_id, fw_version, metric names and text values are at most 64 characters. Numbers must be finite. - The receiver also records its own received_at timestamp for every reading.

Response 200:

{ "stored": 37, "duplicates": 3, "ack_seq": 1042, "server_ts": 1762538455 }
  • ack_seq: the highest seq such that every seq from oldest_buffered_seq up to and including it is stored for this node. It is null if oldest_buffered_seq itself is not stored. The node deletes everything up to and including ack_seq from its buffer, and deletes nothing on null.
  • Because the run starts at the node's own buffer floor, a missing reading holds the ack back only until the node's floor moves past it. A permanently lost reading cannot stall acks. The node should send oldest readings first.
  • Commit the whole batch in one transaction before responding.

Validation errors return 422 with details. The receiver must never crash on bad input.

5.2 GET /api/v1/time

Returns { "server_ts": <epoch UTC> }. The node needs a valid clock before it can verify the certificate, so it should use NTP first and treat this as a check. No API key required.

5.3 GET /api/v1/health

Returns { "status": "ok", "db": "ok", "last_reading_at": <epoch|null>, "nodes": ["balcony-01"] }. If the database can't be read, it returns 503 with status and db set to "error". No API key required, but only reachable on the VPS (for example over ssh).

5.4 GET /api/v1/latest?node_id=balcony-01

Returns the reading with the highest seq (its metrics plus seq, ts, ts_synced, received_at, fw_version), for quick checks on the VPS. An unknown node returns 404. Requires the API key, sent as a header only. The ?key= option is removed, because nginx logs full URLs. The dashboard replaces the browser check.

5.5 Security requirements for the node firmware

The firmware is a separate project, but the receiver's security depends on it. The firmware must meet these:

  • Verify the server certificate against root certificates built into the firmware: ISRG Root X1 and ISRG Root X2, the Let's Encrypt roots. Never turn verification off, for example with setInsecure(), even while testing. Without this check, anyone on the home WiFi or the router path could pose as the server, take the API key and send a false time.
  • Check the hostname as well as the certificate chain.
  • Get the time from NTP before the first HTTPS request, since certificate checks need a valid clock. Use /api/v1/time only as a check.
  • Keep the API key out of the firmware repo. Load it from a local, gitignored config at build time.
  • Expose no network services. The node only makes outgoing requests.
  • Optional: ESP32 flash encryption, so a stolen node doesn't easily give up its key. The cost is that reflashing gets harder, and a mistake can lock the board. Decide this before the first deployment.

If a node is lost or stolen, rotate the API key (see the README). The old key then returns 401.

6. Storage

6.1 Schema (long format, so adding sensors needs no schema changes)

CREATE TABLE readings (
  node_id      TEXT    NOT NULL,
  seq          INTEGER NOT NULL,
  ts           INTEGER NOT NULL,     -- node clock, epoch UTC
  ts_synced    INTEGER NOT NULL,     -- 0/1
  received_at  INTEGER NOT NULL,     -- server clock, epoch UTC
  fw_version   TEXT,
  PRIMARY KEY (node_id, seq)
);

CREATE TABLE metrics (
  node_id  TEXT    NOT NULL,
  seq      INTEGER NOT NULL,
  name     TEXT    NOT NULL,
  value_num REAL,
  value_txt TEXT,
  PRIMARY KEY (node_id, seq, name),
  FOREIGN KEY (node_id, seq) REFERENCES readings(node_id, seq)
);

CREATE INDEX idx_readings_ts ON readings(ts);
CREATE INDEX idx_metrics_name ON metrics(name);
  • Use INSERT OR IGNORE for duplicate handling.
  • Enable PRAGMA journal_mode=WAL.
  • Store raw values only, in SI units. Conversions (°F, PPFD, DLI) are computed on output.

6.2 Derived values (derived.py)

  • ppfd_umol = lux / 54. This is the sunlight approximation. Keep the factor configurable.
  • DLI (mol/m²/day) = sum over the day of ppfd × interval_seconds / 1,000,000, using the real gaps between consecutive readings (capped at 30 minutes so long data gaps don't inflate it). Days are local America/New_York calendar days. Report how much of the day the data covers.
  • Sun window: first and last time each day that lux is above a threshold (default 20,000 lux, configurable), as a rough "direct sun on the railing" indicator.
  • c_to_f(c) = c × 9/5 + 32.

6.3 Dashboard (dashboard.py)

  • A read-only page at /dashboard, served by the receiver. It needs no second service.
  • Charts for the last 7 days: air and tray temperature (°F), lux, pellet moisture and battery voltage, each with a marker for gaps in the data.
  • Today's latest reading, and the daily summary table from derived.py.
  • Plotly's JavaScript is served by the app, not a third-party CDN.
  • Works on a phone.
  • Warnings for readings that look wrong, so tampering or a faulty sensor shows up. It flags values outside physical ranges (for example air temperature outside −40 to 60 °C, humidity outside 0 to 100%, negative lux), jumps in seq of more than 1,000 above the previous one, ts more than a day away from received_at, and any node_id other than the known ones. Warnings only. Nothing is deleted or rejected. The ranges live in one place in the code.
  • Login is nginx basic auth. The app has no user accounts, so the dashboard must never be published except through nginx.

7. Scripts

  • fake_node.py: posts realistic fake data (daytime light curve, temperatures that drop overnight). Flags: --batch N, --resend (repeats the last batch to test duplicate handling), --gap HOURS (simulates the VPS being unreachable), --url (full base URL, so it can test HTTPS), --key.
  • export_csv.py: wide CSV with one row per reading and one column per metric, plus *_f columns for temperatures. Flags: --from, --to dates, --node.
  • daily_summary.py: a table per day with min/max air temperature (°F), min/max tray temperature (°F), hours below 45°F, DLI, sun window start/end, data coverage %.
  • backup_db.py: a consistent copy using SQLite's backup API, safe while the receiver runs. Keeps 14 daily copies. Runs nightly from Carlos's cron.

8. VPS setup (each step needs Carlos's OK; he runs anything that needs sudo)

  1. Readiness: before deploying, confirm who else can log in, check ufw, and check from outside whether services published on 0.0.0.0 are reachable. Docker-published ports usually bypass ufw.
  2. DNS: add an A record for station.carlosgorrichoai.one pointing to the VPS.
  3. Container: clone to ~/apps/balcony-station-receiver, create .env with a new API key, and run docker compose up -d. The compose file sets restart: unless-stopped, publishes 127.0.0.1:8765 only, and keeps data/ and logs/ in mounted folders. The container runs as a non-root user, with a read-only filesystem except for those two folders and a small /tmp, all Linux capabilities dropped, and no-new-privileges set. Docker group membership covers this step, so no sudo is needed.
  4. nginx (sudo): install deploy/nginx-station.conf as a new site. It allows the paths in Section 5 only, limits request size to 1 MB, rate limits the public paths, and adds auth_basic to /dashboard. Test with nginx -t before reloading, because other live sites share this nginx.
  5. Certificate (sudo): issue it with certbot --nginx -d station.carlosgorrichoai.one.
  6. Dashboard login (sudo): create the password file with htpasswd, outside the repo.
  7. Backups: add a nightly cron entry for backup_db.py. Keep at least one copy off the VPS, because a copy on the same disk doesn't survive losing the server.
  8. Smoke test: from a phone on mobile data, open the dashboard and log in.

9. Build order and acceptance criteria

  1. Scaffold: folder, git, uv env, dependencies, .env generated with a random key. uv run pytest passes (empty).
  2. Ingest: the POST /readings endpoint plus storage. Tests cover: valid batch stored; resent batch → all duplicates, no new rows; out-of-order seqs; gap in seqs → ack_seq stops before the gap, then advances once it is filled; oldest_buffered_seq moved past a gap → ack_seq advances; oldest_buffered_seq not stored → ack_seq is null; oldest_buffered_seq above the batch → 422; unknown metric names stored; bad key → 401; malformed body → 422 with no crash.
  3. Other endpoints: /time, /health, /latest, with tests.
  4. Derived values and scripts: DLI test using a synthetic day with known lux values gives the expected value within 1%. Fake node, CSV export and daily summary all run against a test database.
  5. Logging: a rotating file log in logs/ (5 × 1 MB) records each batch (node, stored, duplicates, ack_seq, client IP) and every error. A test confirms the API key never appears in the log.
  6. Production hardening: remove ?key=; turn off /docs, /redoc and /openapi.json; trust forwarded client IPs from STATION_FORWARDED_ALLOW_IPS only; give fake_node.py a --url flag. Remove the Windows install scripts. Tests cover each change.
  7. Dashboard: the page in 6.3, with tests for empty data, gaps, text metrics and each warning.
  8. Packaging: Dockerfile, compose file, nginx template and backup_db.py. The image builds and passes the Done-when scenario locally on Linux, running as the non-root user with the read-only filesystem from Section 8. A restored backup opens and holds the expected rows.
  9. README: rewritten for the VPS: deploy, update, start and stop, view the dashboard, export CSV, run the daily summary, rotate the API key, restore a backup, and remove the site.
  10. Server readiness: Section 8, steps 1 and 2.
  11. Deploy: Section 8, steps 3 to 7.
  12. End-to-end: the Done-when scenario below, over the real HTTPS address.

Done when: fake_node.py running from the laptop pushes 24 hours of simulated data to the public HTTPS address, as a throwaway node ID, including one resend and one 6-hour gap. The database then holds no duplicates, daily_summary.py prints a correct table, and the dashboard shows the same data. From outside the VPS, /docs, /api/v1/health and /api/v1/latest return 404, /dashboard returns 401 without a login, and port 8765 is closed. The test data is then removed. The API key appears in no log, including nginx's.
